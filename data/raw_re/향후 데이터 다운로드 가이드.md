# 향후 데이터 다운로드 가이드

- 최종 링크 확인일: 2026-08-15 KST
- 적용 범위: `프로젝트 계획서.md`의 RE Stage 1~9
- 목적: 사용자가 필요한 시점에 공식 원문·파일·API를 직접 확보할 수 있도록 데이터명, 링크, 수집 시점, 범위, 저장 위치와 사용 제한을 한곳에 고정한다.
- 실행 상태: 이 문서는 다운로드 안내서다. 현재 턴에서는 데이터 다운로드, API 활용신청, 인증키 발급, 원문 첨부파일 저장을 실행하지 않았다.

---

## 1. 먼저 지킬 원칙

1. RE Stage 1 승인 전에는 새 외부데이터를 대량 다운로드하지 않는다.
2. 공식 데이터셋 페이지를 기준 링크로 사용한다. 로그인 세션에 따라 달라지는 임시 파일 URL은 문서에 고정하지 않는다.
3. API 인증키는 `.env`에만 보관하고 Markdown, Git, 로그, 스크린샷에 기록하지 않는다.
4. 기존 `data/raw/`의 Stage 1 원본은 덮어쓰지 않는다.
5. 새 데이터는 RE Stage 1에서 경로 승인을 받은 뒤 `data/raw_re/<source>/<기준일 또는 기준분기>/`에 저장한다.
6. 다운로드한 원본의 URL, 원본 파일명, 수집일시, 게시일·수정일, 기준기간, 파일 크기, SHA-256, 라이선스를 Manifest에 기록한다.
7. 정책 공고는 목록 페이지의 요약값만 저장하지 않는다. 반드시 공고 원문, 첨부문서, 신청 페이지까지 함께 보존한다.
8. 현재 시점 Snapshot을 과거 시점 Feature로 소급 사용하지 않는다. 과거 Snapshot이 있는 데이터만 시간순 학습 Feature 후보로 사용한다.
9. 선택 데이터는 같은 Fold와 Target에서 단독 Ablation을 통과한 경우에만 유지한다.

### 2.1 공통 사용 흐름

다운로드한 파일을 곧바로 모델이나 서비스가 읽게 하지 않는다. 모든 데이터는 다음 순서를 거친다.

```text
공식 원본·API 응답
→ data/raw_re 원본 보존
→ 출처·기준일·스키마·중복·결측·시간누수 QA
→ data/processed_re 표준 테이블
→ 정책 지식베이스 / 현금흐름 엔진 / Panel v2 후보 중 목적에 맞는 한 곳에만 투입
→ 동일 기준선 Ablation 또는 규칙 단위 테스트
→ Gate 통과 데이터만 서비스 사용
```

공통 결합 기준은 다음과 같다.

| 데이터 유형 | 기본 시간 키 | 기본 공간 키 | 업종 키 | 사용 단위 |
| --- | --- | --- | --- | --- |
| 기존 서울 상권 1~9종 | `기준_년분기_코드` | `상권_코드` | 있으면 `서비스_업종_코드` | 분기×상권×업종 또는 분기×상권 |
| 상가정보 Snapshot | Snapshot 기준일을 분기로 변환 | 좌표를 영역-상권 Polygon에 공간결합 | 상가정보 업종→서울 서비스업종 매핑 | 분기×상권×업종 집계 |
| 지방행정 인허가 | 인허가일·폐업일·변경일을 분기로 변환 | 좌표 우선, 주소 보조 공간결합 | 인허가 업종→서울 서비스업종 매핑 | 분기×상권×업종 집계 |
| ASOS 날씨 | 관측일→분기 | 서울 108 지점은 서울 공통 | 없음 | 분기 공통 Feature |
| 공휴일 | 날짜→분기 | 전국 공통 | 없음 | 분기 공통 Feature |
| 문화행사 | 시작일·종료일→분기 | 좌표·주소→상권 | 없음 | 분기×상권 Feature |
| 실시간 도시데이터 | 수집시각 | 121장소 영역→상권 | 없음 | 운영시점 장소·상권 Context |
| 정책 공고 | 공고일·적용기간·접수기간 | 전국·서울 등 `region_scope` | 공식 대상업종·제외업종 | 정책 버전 |
| 개인 현금흐름 입력 | 실제 입출금 예정일 | 사용자 선택 상권 | 사용자 선택 업종 | 개인 사업장 시뮬레이션 |

### 2.2 정책 데이터는 언제 어떻게 사용하는가

| 데이터 | 사용 시점 | 처리 방법 | 최종 사용처 | 직접 계산 사용 |
| --- | --- | --- | --- | --- |
| 기업마당 API | RE2 후보 탐색 | 당해 연도 전체 응답→지원대상·지역·기관·키워드 필터→공고 URL 추출 | 전체 후보 목록 | 금지 |
| 소상공인24 | RE2 원문 검증 | 후보별 상세 페이지·첨부문서에서 소상공인 대상과 신청조건 대조 | 공식 자격근거 | 검수 후 가능 |
| 소진공 정책자금 | RE2 구조화, RE4 금융 이벤트, RE6 자격판정 | 세부 공지 단위로 직접·대리대출, 금리, 한도, 거치·상환, 제외업종 구조화 | 정책 Metadata·자격규칙·상환 이벤트 | 공식 숫자만 가능 |
| 서울시 육성자금 | RE2 구조화, RE4 금융 이벤트, RE6 자격판정 | 최초공고와 변경공고를 버전 분리하고 적용일 기준 최신 유효조건 선택 | 서울 정책 Metadata·이차보전·융자 이벤트 | 공식 숫자만 가능 |
| 중소벤처24 API | RE2 교차검증 | 기업마당의 공고명·기간·기관·첨부파일 불일치 확인 | 누락·불일치 QA | 금지 |

정책 데이터의 구체적 변환은 다음과 같다.

```text
공고 원문
→ 정책 기본 Metadata
→ 자격조건 Rule
→ 금융조건 Event
→ 공식 문단별 RAG Chunk
```

- 정책 기본 Metadata: 정책명, 기관, 유형, 지역, 업종, 접수기간, 적용기간, 원문 URL
- 자격조건 Rule: 매출, 상시근로자, 업력, 신용·연체, 제외업종, 지역, 중복수혜 조건
- 금융조건 Event: 지급액, 지급예정일, 금리, 보증료, 거치기간, 상환기간, 상환방식, 자부담, 환급지연
- RAG Chunk: 원문 문단, 페이지, 정책 버전, 확인일과 함께 저장
- RE4에서는 금융조건 Event만 현금흐름 엔진에 투입한다.
- RE6에서는 자격조건 Rule만 적격·부적격·추가확인 판정에 사용한다.
- 생성형 AI는 RAG Chunk를 설명에만 사용하고 Rule·Event 값을 바꾸지 않는다.
- RE9 데모 직전 접수상태와 변경공고를 다시 수집해 정책 버전을 갱신한다.

### 2.3 개인 현금흐름 데이터는 언제 어떻게 사용하는가

| 사용 시점 | 처리 | 산출물 | 사용처 |
| --- | --- | --- | --- |
| RE3 입력계약 승인 후 | 월·주 단위 입력을 실제 날짜별 입출금 Event로 변환 | 기준 13주·6개월 현금흐름 | 무개입 Baseline |
| RE4 정책 적용 시 | 정책 지급·비용절감·대출·상환 Event를 기준 현금흐름에 합성 | 정책별 현금곡선 | 개입 시나리오 |
| RE7 비교 시 | 모든 시나리오를 같은 시작일·기간·초기현금으로 비교 | 최저현금, 고갈일, 총부채, 원리금 | 목표별 의사결정 |

- 상권·업종 ML 변화율은 개인 매출에 자동으로 확정 적용하지 않는다.
- `집계 변화율 100% 적용`, `사용자 조정 적용률`, `사용자 직접 충격률`을 별도 시나리오로 구분한다.
- 개인 입력은 정책 자격과 현금흐름 계산에 필요한 값만 메모리에서 사용하고 기본적으로 서버에 저장하지 않는다.

외부환경 데이터의 Ablation 순서는 고정한다.

```text

→ + 인허가 변화

→ + 문화행사
→ 실시간 도시데이터는 운영 Context로 별도 평가
```

각 단계는 같은 Target, 같은 시간순 Fold, 같은 평가 지표를 사용한다. 데이터 추가 전후 성능, 최악 Fold, 업종별 안정성, 결측·Coverage, 처리시간과 서비스 현금흐름 민감도를 함께 비교한다. 증분효과가 없거나 누수·Coverage 문제가 있는 데이터는 다운로드했더라도 최종 모델에서 제외한다.

### 2.6 단계별 최종 전달 경로

| 입력 데이터 | 중간 산출물 | 전달 단계 | 최종 기능 |
| --- | --- | --- | --- |
| 정책 원문·API | 정책 Metadata·Rule·Event·RAG Chunk | RE4·RE6·RE7 | 자격판정, 정책효과 계산, 공식 근거 설명 |
| 개인 입력 | 날짜별 기준 현금흐름 | RE4·RE7 | 13주·6개월 현금곡선과 고갈시점 |
| 서울 상권 1~9종 | Panel v2·Target v2 | RE5 | P10·P50·P90 외부 매출환경 후보 |
| 상가·인허가·날씨·공휴일·행사 | Ablation별 Panel v2 후보 | RE5 | 검증 통과 시 Quantile 모델 Feature |
| 실시간 도시데이터 | 제한지역 운영 Context | RE8 | 현재상황 참고표시, 모델과 분리 가능 |

다운로드 여부와 모델 채택 여부는 같은 결정이 아니다. 다운로드 후 QA와 Ablation을 통과하지 못한 데이터는 원본과 검증기록만 보존하고 서비스 계산에서는 사용하지 않는다.

- 공식 파일 다운로드: [소상공인시장진흥공단_상가(상권)정보](https://www.data.go.kr/data/15083033/fileData.do)
- 공식 업종코드 파일: [상가(상권)정보 업종코드](https://www.data.go.kr/data/15067631/fileData.do)
- 장점: 주기성 과거 데이터가 있으므로 분기 Snapshot을 시간순 Feature 후보로 검증할 수 있다.
- 받아야 할 것:
  - Target 학습기간과 일치하는 분기 Snapshot
  - 각 압축파일에서 서울특별시 데이터
  - 해당 시점의 업종코드·분류표
  - 분류체계 변경 공지
- 대량수집 제한: 과거 데이터 전체를 한 번에 받지 않는다. 먼저 분기 3개 표본으로 파일 크기, 식별자 연속성, 업종코드 매핑을 검증하고 전체 기간 수집 여부를 승인받는다.
- 저장 후보: `data/raw_re/store_snapshot/<기준일>/`

### E-02. 상가정보 운영 API

- 공식 활용신청·명세: [소상공인시장진흥공단_상가(상권)정보 API](https://www.data.go.kr/data/15012005/openapi.do)
- 제공형식: REST, JSON·XML
- 역할: 최신 업소 조회와 서비스 시점 보완
- 제한: 현재 응답을 과거 분기 Feature로 소급하지 않는다. 과거 모델링에는 E-01의 기준일별 Snapshot을 사용한다.
- 저장 후보: `data/raw_re/store_api/<수집일>/`

### 수집 범위 결정 규칙

1. 서울 상권 서비스업종 100개와 인허가 195종의 매핑표를 먼저 만든다.
2. 매핑되는 업종과 좌표·주소·개업일·폐업일·영업상태·이력 조회가 있는 API만 후보로 남긴다.
3. 모든 195종을 무조건 수집하지 않는다.
4. 예측기준일 이후에 등록된 상태변경을 과거 Feature에 넣지 않는다.
5. 업종별 API의 `history` 제공 여부와 기준일 의미를 확인한다.
6. LOCALDATA는 특정 과거일의 완전한 Snapshot을 제공한다고 가정하지 않는다. 인허가일·폐업일·변경일로 과거 상태를 재구성할 수 있는지와 늦은 행정등록에 따른 누수 위험을 먼저 검증한다.

### 파일 준비 방식

1. 각 폴더에 최종 공고문 또는 공식 안내 원문을 보존한다.
2. 사용자가 직접 확인·수정한 본문은 UTF-8 Markdown 하나로 정리한다.
3. 신청서 양식만 있고 자격·금액·기간이 없는 파일은 검색 본문으로 쓰지 않는다.
4. 공식 페이지 URL, 신청 URL, 공고일, 접수기간, 종료 여부를 Markdown에 함께 적는다.
5. PDF가 있더라도 이미지 분석·OCR은 하지 않으며 텍스트 추출이 가능한 원문만 사용한다.
6. 다운로드 완료를 알리면 Codex가 중복·버전·Rule·Event를 검토한 뒤 DB에 추가한다.

API 활용승인 여부:
비고:

인증키 값은 이 양식에 적지 않는다.

## 11. 받지 않거나 나중으로 미룰 데이터

### 현재 MVP에서 받지 않음

- 실제 개인 계좌 거래내역
- 카드매출 원장
- POS 원장
- 개인 신용점수·대출 승인확률 자료
- 개인 점포의 폐업 Label
- 정책 실제 수혜자 개인정보
- 정책의 실제 인과효과 Label

### MVP 이후 기관협력이 있을 때만 검토

- 정책 신청·선정·집행·상환 결과
- 정책 수혜 전후 매출·고용·폐업 성과
- 동의 기반 계좌·카드·POS 연동
- 금융기관 승인·부결 데이터

이 자료는 공개 다운로드 대상이 아니며 개인정보·제휴·법적 근거·인과추론 설계가 먼저다.
