# V5 공모전 기획서 작성 계획

## 1. 이 문서의 역할

이 문서는 공식 양식 `(첨부1) 2026 금융 AI Challenge 공모전 기획서.hwpx`를 다른 세션에서 작성하기 위한 실행 계획이다. 완성 원고가 아니며 공식 HWPX 원본을 수정하지 않는다.

사용자가 한글에서 작성하고 PDF로 변환한다. Codex가 다음 세션에서 맡을 범위는 항목별 원고 초안, 근거 대조, 표현 통일, 수치와 출처 검증이다.

권장 파일 구분은 다음과 같다.

- 원본 보존: `(첨부1) 2026 금융 AI Challenge 공모전 기획서.hwpx`
- 사용자 작성본: `(첨부1) 2026 금융 AI Challenge 공모전 기획서_버팀AI_V5_작성본.hwpx`
- 최종 제출본: `(첨부1) 2026 금융 AI Challenge 공모전 기획서_버팀AI_V5.pdf`

## 2. 확인된 공식 양식

양식에는 팀명, 구성원 성명과 다음 7개 항목이 있다.

1. 서비스 명칭
2. 아이디어 기획 핵심내용 요약
3. 문제 정의 및 제안 배경
4. 서비스 컨셉 및 차별성
5. 활용 데이터 및 생성형 AI 모델 적용 방안
6. 기대 효과 및 확장 가능성
7. 자유 항목

추출된 양식 안내에는 별도 페이지 제한이 적혀 있지 않다. 페이지 수를 임의로 단정하지 말고 공식 양식의 제목, 표 구조와 필수 표시를 유지한다. 안내 문구는 실제 내용으로 교체하되 항목 자체를 삭제하거나 이름을 바꾸지 않는다.

## 3. 작성 전에 확정할 입력

다음 값은 문서 작성 전에 사용자에게 확인한다.

- 데이콘에 등록된 정확한 팀명
- 팀장과 팀원 성명 및 표기 순서
- 제출 서비스명
- 최종 공개 URL
- 문서에 넣을 화면 이미지의 범위

서비스명은 현재 문서명과 화면 브랜드가 다르므로 사용자가 최종 선택해야 한다.

- 프로젝트 공식 명칭: `서울 소상공인 정책금융 영향 시뮬레이터`
- 배포 화면 브랜드: `버팀AI`
- 권장 제출 표기: `버팀AI: 서울 소상공인 정책금융 영향 시뮬레이터`
- 권장 부제: `추가 대출이 현금 위기를 해결하는지, 부채만 늘리는지 계산하는 AI 정책금융 코파일럿`

권장안은 두 이름을 함께 보존하지만, 제출 서비스명 확정은 결과의 정체성을 바꾸는 선택이므로 사용자 승인 뒤 문서 전체에 같은 이름을 사용한다.

## 4. 문서 전체 서사

기획서는 기능 목록을 길게 나열하는 문서가 아니다. 다음 질문이 한 흐름으로 이어져야 한다.

1. 소상공인은 왜 정책을 찾고도 실행 여부를 판단하기 어려운가?
2. 추가 대출이나 지원이 실제 현금 위기를 해결하는지 어떻게 비교할 것인가?
3. 버팀AI는 AI와 결정론 엔진의 역할을 어떻게 나눴는가?
4. 사용자는 서비스에서 어떤 판단을 얻게 되는가?
5. 현재 MVP가 검증한 범위와 검증하지 못한 범위는 무엇인가?

한 문장 중심축은 다음과 같이 유지한다.

> 현금 부족과 기존 부채 사이에서 정책금융 실행을 고민하는 서울 소상공인이, 무대응·비차입 지원·신규 정책자금의 13주 현금과 6개월 부채를 같은 일정에서 비교하도록 돕는다.

### 5.2 아이디어 기획 핵심내용 요약

목표는 심사위원이 30초 안에 사용자, 문제, 핵심 계산, AI 역할과 결과를 이해하도록 만드는 것이다.

권장 구성은 5개 안팎의 짧은 개조식 문장이다.

1. 목표 사용자: 현금 부족과 기존 부채를 함께 안고 정책금융 실행을 고민하는 서울 소상공인
2. 입력: 상권·업종, 최근 매출, 보유 현금, 비용과 대출
3. 핵심 결과: 하방·기준·회복 범위의 13주 현금과 6개월 부채
4. 정책 비교: 무대응과 최대 3개 선택 정책의 현금·부채·상환 부담 비교
5. AI 경계: AI는 시나리오와 공식 공고 설명을 돕고, 자격·금액·효과·순위는 규칙과 금융 엔진이 결정

추가할 수 있는 한 문장:

- 선택 정책의 조건과 공고 핵심정보를 확인한 뒤 공식 신청 경로로 연결한다.

피할 내용:

- 구현되지 않은 계좌·카드·POS 자동 연동
- 자동 신청이나 승인 가능성 예측
- 개인 매출 또는 폐업 가능성 예측
- 실제 정책 수혜 효과를 검증했다는 표현

### 5.3 문제 정의 및 제안 배경

목표는 `정책이 많다`가 아니라 `정책을 이용한 뒤 현금과 부채가 어떻게 달라지는지 판단하기 어렵다`는 문제를 증명하는 것이다.

권장 전개:

1. 현금과 부채 문제가 실제로 큼
2. 위기를 늦게 인지하거나 지원을 제때 쓰지 못하는 문제가 있음
3. 추가 금융지원이 위기를 늦출 뿐 해결하지 못할 수 있음
4. 기존 공개 서비스는 상권분석, 경영진단, 정책 검색과 알림을 이미 제공함
5. 남은 판단 공백은 정책 조건을 개인 사업장의 일정에 적용한 전후 비교임

사용 가능한 현재 근거:

- 폐업 결심 당시 부채 보유 68.5%, 평균 부채 8,531만원
- 폐업 과정 최대 애로 중 대출금 상환 45.5%
- 확대가 필요한 지원으로 상환유예·이자감면 32.1%
- 정상 매출보다 40% 이상 감소한 뒤 폐업을 결심한 비율 64.4%

이 수치는 [`프로젝트 계획서.md`](../프로젝트%20계획서.md) 34절과 [`V6 실제 수요 검증 보고서.md`](../V6%20실제%20수요%20검증%20보고서.md)에 출처와 함께 정리돼 있다. 최종 원고를 쓸 때는 원문 링크, 조사 대상, 조사 시점과 단위를 다시 확인한다.

표현 경계:

- `모든 소상공인이 이 서비스를 원한다`고 쓰지 않음
- 실제 사용자 인터뷰, 사용 로그와 지불 의사는 검증하지 않았다고 구분
- 문제의 실재성과 서비스 수요 검증을 같은 것으로 취급하지 않음

권장 시각자료:

- `정책 발견 → 금액·시점·자부담 확인 → 13주 현금·6개월 부채 비교 → 공식 신청 확인` 흐름도 1개
- 통계는 많아도 3개까지만 본문에 강조하고 나머지는 출처와 함께 보조 설명으로 처리

### 5.4 서비스 컨셉 및 차별성

목표는 `정책 추천 챗봇`이 아니라 `정책 전후 금융결과 비교 도구`임을 분명히 하는 것이다.

권장 전개:

1. 사용자가 상권과 재무정보를 입력함
2. 서비스가 13주 현금과 6개월 부채 기준선을 계산함
3. 정책의 지급, 감면, 자부담, 거치와 상환조건을 같은 일정에 반영함
4. 무대응과 선택 정책을 비교함
5. AI는 검증된 결과와 공식 근거를 설명함

차별성의 핵심 문장:

> 검토한 공개 기능과 달리, 정책의 금액·지급 시점·자부담·상환조건을 개인 사업장의 현금 일정에 적용해 무대응 대비 13주 현금, 6개월 부채, 월 상환액과 총이자를 함께 비교한다.

반드시 지킬 표현:

- `유일한 서비스`, `국내 최초`, `기존에 없는 서비스`로 단정하지 않음
- `검토한 공식 공개 기능과 다른 의사결정 단위`라고 한정
- 상권분석, 경영진단, 정책 검색과 알림 자체를 독창성으로 주장하지 않음

권장 시각자료:

- 무대응·비차입 지원·신규 정책자금의 비교 결과 화면 1개
- `AI 설명`과 `결정론 엔진의 금융 권한`을 나눈 구조도 1개

### 5.5 활용 데이터 및 생성형 AI 모델 적용 방안

목표는 데이터 출처와 AI 역할을 기능별로 설명하고, AI가 금융 결과를 임의로 만들지 못하도록 한 설계를 보여주는 것이다.

데이터는 다음 네 묶음으로 정리한다.

1. 서울 상권·업종 집계 데이터와 학습용 시계열 데이터
2. 사용자가 직접 입력하는 최근 매출, 보유 현금, 비용과 대출
3. 공식 정책 공고, 자격조건과 금융조건
4. 정책 Event와 결정론 현금흐름 계산용 구조화 데이터

AI와 비AI 역할은 표로 나누는 것을 권장한다.

| 구성 | 역할 | 결정하지 않는 것 |
| --- | --- | --- |
| LightGBM Quantile 모델 | 상권·업종 집계의 하방·기준·회복 매출환경 시나리오 | 개인 매출과 폐업 가능성 |
| Luna 기반 What-if 해석 | 사용자가 동의한 가정 문장의 제한된 의도 해석 | 재무값과 계산 결과 |
| Luna 기반 공고 구조화 | 저장된 공개 공고에서 신청 기간, 금융 조건, 신청 경로, 서류, 문의처, 게시일 구조화 | 최종 자격과 승인 |
| 공식 Rule·정책 Event·현금흐름 엔진 | 자격 상태, 금액, 조건부 효과, 현금과 부채 계산 | 생성형 AI의 자유 추정 |
| 근거 검증 하네스 | Chunk, 인용문과 숫자 근거를 확인하고 실패 시 값을 비움 | 근거 없는 보완 |

개인정보 경계:

- 사용자 재무정보는 장기 저장하지 않음
- 재무값과 계산 결과를 외부 AI에 보내지 않음
- 공개 저장 공고만 공고 구조화에 사용
- 사업자등록번호, 주민등록번호, 계좌번호, 카드번호와 개인 신용점수는 수집 대상이 아님

### 5.6 기대 효과 및 확장 가능성

목표는 현재 MVP에서 기대할 수 있는 의사결정 효과와 향후 검증이 필요한 확장을 분리하는 것이다.

현재 MVP에서 기대하는 효과:

- 추가 대출이 단기 현금 부족을 해결하는지, 부채만 늘리는지 함께 확인
- 비차입 지원을 신규 대출과 같은 화면에서 비교
- 정책 지급 지연, 자부담과 거치 종료 후 부담을 사전에 점검
- 상담이나 신청 전 확인할 조건과 공식 공고 항목을 정리
- AI 설명이 실패해도 핵심 계산과 비교를 계속 수행

현재 검증하지 못한 효과:

- 실제 신청률이나 정책 수혜율 증가
- 폐업 감소와 매출 개선
- 모든 소상공인의 반복 사용 의사
- 정책의 인과 효과

향후 확장안은 구현 기능과 섞지 않고 `검증 후 확장`으로만 쓴다.

- 상담자, 세무사 또는 지원기관의 반복 상담 보조 도구
- 사용자 동의와 제휴가 확보된 회계·거래자료 연동
- 최신 공고 운영과 사후 성과데이터를 이용한 효과 검증
- 금융상품 중개나 자동 신청으로 넓힐 경우 별도 법률·개인정보 검토

### 5.7 자유 항목

## 6. 시각자료 계획

페이지 제한이 공식적으로 확인되지 않았더라도 그림을 많이 넣어 본문을 밀어내지 않는다. 권장 우선순위는 다음과 같다.

1. 대표 사례의 무대응·비차입 지원·신규 정책자금 비교 화면
2. 진단 → 비교 → 준비 사용자 흐름
3. AI와 결정론 엔진의 권한 분리 구조

화면 이미지는 공개 배포본에서 합성 또는 가상 입력만 사용해 캡처한다. 실제 개인정보가 보이는 이미지는 넣지 않는다. 캡처 날짜와 화면 이름을 관리하고, 문서에 넣은 이미지가 최종 배포 화면과 같은지 사용자 본인이 확인한다.

기본 역할 분담은 다음과 같다.

- Codex: 문서에 필요한 화면 목록, 캡처할 상태와 범위, 권장 구도, 이미지 번호와 캡션 초안을 준비한다.
- 사용자: 공개 배포 사이트에서 대표 사례나 가상 입력으로 직접 캡처하고 HWPX에 삽입한 뒤 크기, 자르기와 페이지 배치를 조정한다.
- Codex: 변환된 PDF를 전달받으면 본문과 화면의 일치, 수치·캡션 누락, 글자와 이미지 잘림 가능성을 점검한다.
- 사용자: 최종 화면 품질과 PDF 시각 승인을 담당한다.

사용자가 별도로 요청하면 Codex가 배포 사이트의 원본 캡처 파일 생성을 도울 수 있다. 다만 HWPX 삽입과 최종 배치는 사용자가 직접 하는 것을 기본으로 한다.

## 7. 다른 세션의 실행 순서

1. 이 계획과 공식 HWPX 양식, `v5/README.md`, `v5/VERIFICATION.md`를 읽는다.
2. 팀명, 구성원, 제출 서비스명과 최종 URL을 사용자에게 확인한다.
3. 기획서에 사용할 주장 목록을 `확인됨`, `조건부`, `미검증`으로 분류한다.
4. 3번 문제 정의를 먼저 작성하고 4번 차별성으로 연결한다.
5. 5번 AI·데이터 역할표와 개인정보 경계를 작성한다.
6. 6번 기대 효과에서 현재 효과와 향후 확장을 분리한다.
7. 2번 요약을 마지막에 작성해 본문과 일치시킨다.
8. 7번 자유 항목에 검증과 한계를 배치한다.
9. 사용자에게 HWPX 입력용 최종 원고와 캡처 목록·구도·캡션을 항목별로 전달한다.
10. 사용자가 공개 배포 사이트에서 가상 데이터로 화면을 캡처한다.
11. 사용자가 원고와 화면 이미지를 HWPX 작성본에 직접 넣고 페이지 배치를 조정한다.
12. 사용자가 PDF로 변환한다.
13. 변환된 PDF에서 글자 잘림, 표 넘침, 이미지 해상도, 캡션, 링크와 페이지 순서를 사용자와 함께 확인한다.

## 8. 최종 검수 체크리스트

- [ ] 팀명과 구성원 순서가 데이콘 등록정보와 같음
- [ ] 서비스명이 기능명세서와 배포 화면 설명에 맞음
- [ ] 모든 통계에 조사 대상, 시점과 출처가 있음
- [ ] 실제 사용자 검증을 했다고 쓰지 않음
- [ ] 개인 매출, 폐업, 승인 가능성을 예측한다고 쓰지 않음
- [ ] AI와 결정론 엔진의 역할이 분리돼 있음
- [ ] 구현된 V5와 향후 확장 기능이 명확히 구분됨
- [ ] 차별성을 `검토한 공개 기능` 범위로 한정함
- [ ] 기획서 요약과 본문에 숫자·용어 충돌이 없음
- [ ] 화면 이미지는 대표 사례나 가상 입력만 사용하고 실제 개인정보가 없음
- [ ] 각 이미지의 캡션이 본문 기능과 실제 화면에 일치함
- [ ] 원본 HWPX가 보존돼 있음
- [ ] 최종 PDF에서 글자와 표가 잘리지 않음

## 9. 작성 중 멈춰야 하는 경우

다음 선택이 생기면 임의로 정하지 않고 사용자 확인을 받는다.

- 제출 서비스명 또는 목표 사용자 변경
- 문제 정의나 차별성의 중심 변경
- 검증하지 않은 통계나 성과 추가
- 실제 구현보다 넓은 서비스 범위 기재
- 개인정보 처리나 외부 AI 전송 범위 변경
- 향후 확장을 현재 구현처럼 표현해야만 문장이 성립하는 경우
